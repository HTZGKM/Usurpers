# 已确认业务规则与本轮验收

本文件记录本轮讨论后确定的实现要求。课程 Topic 02 是 Restaurant Booking and Ordering Website；课程 PDF 是需求背景，本文以用户本轮确认的营业规则为准。正式环境为 Vercel + Neon PostgreSQL，SQLite 仅保留隔离兼容回归用途。

| 范围 | 规则与验收重点 |
| --- | --- |
| 在线选桌 | 顾客选择能容纳人数的最小已配置桌型；前台可例外安排大桌，但不能突破容量、实际占用或预约保护区间。不能通过 API 绕过。 |
| 一账号一桌 | 不同日期也不能同时持有第二笔有效预约；入座未结束、转普通等位未完成仍算当前履约。并发提交只成功一笔。 |
| 到店与改约 | 先校验实际人数。换桌检查新旧时段、之后的预约与清台空间；原记录保留到更换成功。换桌保留预约号、同步预点单桌号并记录操作人、时间、新旧桌号。 |
| 转等位 | 顾客增员导致无法安排，按转等位时刻重新排队；餐厅原因保留预约资格。转普通等位保留历史预约和原价预点单，移除旧留桌；真正入座才进入厨房。 |
| 餐段结束 | 普通等位和叫号只在当前餐段有效，离队或餐段结束同时取消关联未制作预点单。餐厅原因的预约等待由前台协调。 |
| 排序 | 先匹配容量与可用区间，再按已到店预约的预约时间/到店时间排序，普通等位按取号时间；提前到店不抢走更早应到预约。 |
| 取消与竞争 | 修改、取消使用已展示版本；旧页面不能取消别人刚修改的内容。取消与开做在同一写入边界竞争，已经制作的明细不能普通取消。 |
| 售完 | 厨房人工切换可售状态，不引入数量库存。售完先提交则新订单拒绝，顾客保留购物袋并看到售完；已接受订单不会静默撤销，制作中菜品继续。 |
| 缺菜与换菜 | 未开始菜品可报缺；前台征得顾客同意后取消或新建关联替换订单。原订单其他菜品在问题解决后可独立备齐上菜，无需等待替换单制作完成。失败保持待协调状态。 |
| 厨房三队列 | 等待、制作中、整单待上菜。制作中逐菜标记完成；全部未取消菜品备齐且无未处理问题，整单才进入待上菜。 |
| 制作上限 | 初始同时制作 5 笔订单，厨房与主管可以调整，有版本检查和审计。调低不打断已开始订单；未低于新上限前不再开新单。 |
| 上菜权限 | 前台或主管确认整单已上菜，厨房端不能上菜；重复确认不产生重复结果。 |
| 结账 | 同一就餐所有菜品上齐或取消、换菜协商已处理，才允许整桌结账。提交确认的订单集合和总额；旧逐单付款接口不能绕过。付后加单重新形成余额。页面标注模拟收款。 |
| 清台 | 结账、结束就餐后仍处于清台占用；计时只提醒。前台确认清台完成才释放并可叫号。 |
| 身份规范 | 手机号统一归一、校验，顾客不能自行改登录手机号，可改姓名。停用前提交的业务保留，停用先提交则在途新写入被拒绝；员工仍可处理存量业务。 |
| 邮箱恢复 | 登录后验证绑定邮箱，换邮箱验证成功前旧邮箱保留。找回只发已验证邮箱；短期、哈希、单次令牌，频率限制与统一响应。成功重置撤销所有旧会话。 |
| 记录关联 | 同手机号不自动授权查看现场记录。前台请求关联后顾客明确确认；确认前只展示必要信息，关联仍受一账号一桌限制。 |
| 后台任务 | 独立 worker 推进逾时、叫号、餐段结束与预点单，不自动清台、不代替厨房开做、不强制换菜、不取消餐厅原因等待。并发 tick 可重试。 |
| 报表 | 北京时间：收款按 paid_at，订单按 created_at，有效与取消数分开，就餐按真实入座日。菜品名称、分类、成交价快照保留；原有近 30 天展示、趋势与汇总继续保留。旧数据无法还原的改名历史以迁移时已知信息为基准。 |

## 上线与外部服务

1. 在正式应用部署前，以原有 005 为基线执行 `python -m restaurant.db.upgrade --dry-run`，审核后执行 `python -m restaurant.db.upgrade`。006–008 均使用事务及业务写锁，可重复运行；迁移不取消现有预约。
2. 合并后 GitHub 自动部署 Vercel，验证四种角色与新入口。不要将正式业务写入用作并发试验。
3. 邮件环境变量见 `.env.example`。未配置真实 SMTP 时明确显示服务未配置；模拟邮件测试不能替代真实收发验收。密码只在托管平台密钥配置中填写。
4. 独立进程运行 `python -m restaurant.scheduler --interval 15`；支持 `--once`。容器入口见 `deploy/worker.Dockerfile`，由托管平台注入正式 DATABASE_URL 并设置失败重启。需要真实 worker 托管后，才能验收“关闭所有浏览器也持续运行”。当前没有选定托管平台，不能把代码入口当成已部署服务。

Vercel 调度的套餐限制和 GitHub 定时工作流的延迟需在选择托管时核实，不能把尽力触发的任务当作准秒计时：[Vercel 官方说明](https://vercel.com/docs/schedules/cron-jobs/usage-and-pricing)、[GitHub 官方说明](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)。数据库时间与业务写入校验仍是预约冲突的最终依据。

## 回归证据

验收覆盖隔离 PostgreSQL 中的真正并发、事务失败回滚和迁移重跑，SQLite 兼容回归，以及 JavaScript 的旧页面、丢失响应、账单、整单队列与日期统计。具体用例见 `tests/test_confirmed_reservation_rules.py`、`tests/test_account_postgres.py`、`tests/test_account_recovery.py`、`tests/test_reporting_rules.py` 与订单专项测试。最终执行数量和部署结果写入 PR，不在这里固定易过时的通过数量。
